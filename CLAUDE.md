# CLAUDE.md — standing instructions for Claude on this project

This repo is the EE 5113 (VLSI System Design, UTSA) two-person final project:
**Low-Precision Hardware Accelerator for Voice Keyword Recognition**. The pipeline is:
- Python: train, then quantize to INT8/INT4.
- Verilog: the accelerator.
- Genus + Innovus (gpdk045, on `crosby3.utsarr.net`): the ASIC flow.
- Vivado on a Nexys 4 (Artix-7): the board demo.

Two students work on it from Mac, Windows and crosby3, and GitHub is how they stay in sync.

## Keep everyone on the same page (REQUIRED)

1. **After every significant advancement**, create
   `docs/progress/YYYY-MM-DD-<short-milestone>.md` from `docs/progress/TEMPLATE.md`.
   Examples of what counts:
   - a model was trained or retrained
   - weights were re-exported
   - RTL changed and passes simulation
   - a Genus, Innovus or Vivado run finished with new numbers
   - a new tool, script or setup step was added
   - a problem was solved that the other partner would hit too

   Each log must contain:
   - what was done and why
   - the **exact commands** to reproduce it, and on which machine (laptop / crosby3 / Vivado PC)
   - the files added or changed, and where they go or get loaded
   - key results (accuracy, area, power, Fmax, utilization, slack)
   - open issues and next steps
2. **Whenever a setup step, tool version, path or command changes**, update
   `docs/SETUP.md` in the same commit. A partner following SETUP.md from
   top to bottom on a fresh machine must end up with a working environment.
3. Add a one-line entry to the **Progress log** table in `README.md` that links to the new file.
4. Commit the docs **together with** the work they describe. Use clear
   messages such as `rtl: ...`, `flow: ...`, `fpga: ...`, `docs: ...`, `results: ...`.

## Ground rules for changes

- `python/kws_common.py::int_forward` is the golden model. Any arithmetic change
  must be made in both it and `rtl/` (fc_layer/relu/argmax). After the change, rerun
  `./sim/run_sim.sh int8` and `int4`; both must print `TEST PASSED`.
- `weights/<prec>/*` is generated by `python/quantize_export.py`. Never hand-edit it.
- Library paths for the ASIC flow are in `flow/config.tcl` only.
- Never commit tool run directories (`work/`, `fpga/work/`, `*.enc.dat`, logs).
  Curated reports go into `results/<int8|int4|fpga>/`; use `./flow/run.sh save <prec>`.
- Cadence tools run only on crosby3. Claude usually runs on a laptop, so the loop is:
  1. Edit here and push.
  2. The student runs `git pull` on crosby3, then `./flow/run.sh ...`.
  3. The student commits the results and pushes.
  4. Claude reads `results/` to plan the next step.

## Handy commands

```bash
python python/quantize_export.py --synthetic   # placeholder weights (no dataset)
python -m unittest discover -s python -p "test_*.py"     # unit tests (no dataset)
python python/train.py && python python/quantize_export.py   # real model
./sim/run_sim.sh int8          # RTL vs golden (also int4)
./sim/run_sim.sh int8 fpga     # board-level test of fpga/fpga_top.v
./flow/run.sh all int8         # crosby3: Genus + Innovus
./flow/run.sh save int8        # copy reports into results/int8
fpga\build.bat int8 nexys4ddr program   # Windows + Vivado
```
